## Part 1 — Token / Cost Optimization

### What I did

The baseline agent stuffed the entire document corpus, all few-shot examples, and the full conversation history into every single API call. That came to **51,338 input tokens per query** — expensive and slow at scale.

I applied two concrete optimizations:

**Optimization 1 — Retrieval-Augmented Generation (RAG)**

Instead of injecting all documents (~49,000 tokens) into the system prompt on every call, I chunked the documents at index-time and retrieve only the top-k most relevant chunks at query-time. A typical query now includes 2–3 chunks (~200 tokens) rather than the full corpus.

**Why:** The model doesn't need the entire knowledge base to answer a single question. Semantic search finds the relevant sections in milliseconds. This is the highest-leverage token optimization available — it attacks the biggest cost driver directly.

**Optimization 2 — Sliding-window + rolling summary for history**

Instead of resending the full conversation history on every turn (which grows unbounded), I keep only the last N turns verbatim and replace all earlier turns with a single compressed summary (~60 tokens) that the model generates once and caches.

**Why:** Conversation history is the second-biggest token sink in long-running agent sessions. A summary preserves all decisions, facts, and commitments without the verbatim overhead. The quality tradeoff is minimal — the model loses word-for-word recall of early turns, which almost never matters in practice.

**Bonus — Prompt caching**

Stable content (persona, instructions, retrieved chunks) is placed at the head of the prompt so OpenAI's server-side KV cache hits on it. No code change needed — just ordering discipline.

**Why:** Cache hits cost ~75% less and return ~35% faster. Zero quality impact since the content is identical.

### Before / After

| Metric | Before | After | Change |
|--------|--------|-------|--------|
| Input tokens | 51,338 | 404 | **−99.2%** |
| Cost per query (gpt-4o @ $5/1M) | $0.2567 | $0.0020 | **−99.2%** |
| Cost at 10,000 queries/day | $2,567/day | $20/day | **−$2,547/day** |

Run it yourself:
```bash
python part1_token_optimization/token_counter.py
```

### Quality tradeoffs

- **RAG:** near-zero impact for single-domain queries. Edge case: a multi-topic query may miss a relevant chunk if k is too small. Mitigated by raising k for ambiguous queries and adding a topic router.
- **Sliding-window summary:** the model loses verbatim recall of early turns. Nuanced early-turn commitments are the edge case to watch. The summary is generated by the model itself with an explicit "summarise this conversation accurately" prompt, so the information is not lost — just compressed.
- **Prompt caching:** no tradeoff. Identical inputs, server reuses KV cache.

## Part 2 — Debugging

### What I did

I built a broken multi-step pipeline with three intentional bugs that reproduce the three failure modes described — intermittent timeout, malformed output, and silent wrong data. Then I fixed all three and wrote regression tests for each fix.

### The three bugs and how I found them

**Bug A — Silent wrong data (mutable default argument)**

```python
# BROKEN
def fetch_user_context(user_id: str, _cache: dict = {}):  # shared across ALL calls
```

Python creates the default dict once at function definition time. Every call shares the same object. In a concurrent or sequential system, user data from one request bleeds into another with no error, no exception — just silently wrong results.

**How I found it:** Added `pipeline_run_id` to every log line, then compared `user_id` in the request vs `user_id` in the returned context across sequential calls. They didn't always match.

**Fix:** Replace the mutable default with an injected `UserContextCache` class that has proper TTL, per-caller isolation, and no shared state.

---

**Bug B — Intermittent timeout (no timeout on LLM call)**

```python
# BROKEN
def generate_summary(context):
    return _mock_llm_call(prompt)  # no timeout — hangs if upstream is slow
```

The LLM call had no timeout. When the upstream was slow (20% of the time in the mock), the entire pipeline hung indefinitely.

**How I found it:** Added per-step duration logging. Saw `step=generate_summary duration_ms=30412` on ~20% of calls. Looked at the source — no `timeout=` parameter, no `threading.Timer`, no `asyncio.wait_for`.

**Fix:** Run the LLM call on a daemon thread, `join()` with a timeout, raise `TimeoutError` on hang. Add exponential-backoff retry (max 3 attempts, delays: 2s → 4s → 8s).

---

**Bug C — Malformed output / null scores (brittle regex)**

```python
# BROKEN
match = re.search(r"Score:\s*(\d+)", response)
return int(match.group(1)) if match else None  # None stored in DB silently
```

The regex only matched if the model responded with exactly `"Score: <number>"`. Real LLMs frequently include preamble ("Based on the information provided, I would score this lead: 85/100."). In that case the regex returned `None`, which then propagated silently to the database as a null score — no warning, no exception.

**How I found it:** Added `assert score is not None` after `score_lead()` in local tests. It failed ~40% of the time. Printed the raw LLM response and immediately saw the preamble.

**Fix:** Replace the exact-match regex with a general number-extraction scan (`\b([0-9]{1,3})\b`) that finds any integer in [0, 100]. Fall back to a safe default (50) if still nothing found, and always log a warning — never silently fail.

### Debugging process (general)

1. **Triage first** — run the pipeline 30 times, count `{success, null_score, wrong_user, timeout}`. Know the failure rate before touching code.
2. **Force determinism** — set `random.seed(42)`, raise failure probability to 100% for the specific bug. Turns a flaky test into a guaranteed-failing test.
3. **Isolate by step** — comment out steps 2–4, confirm step 1 works alone. Add each step back. The broken step is where failures start.
4. **Scan for three patterns** — (a) external I/O without timeout/retry, (b) shared mutable state, (c) output parsing that assumes a fixed model format.
5. **Write the failing test first** — proves you understand the bug. Fix the code, test goes green, becomes a permanent regression guard.
6. **Deploy with a feature flag** — 1% traffic slice, watch metrics for 15 min, then full rollout.

## Part 3 — CI/CD and Deployment

### What I did

Set up two GitHub Actions workflows and a minimal FastAPI app with health, version, and pipeline endpoints.

### CI pipeline (`ci.yml`) — triggers on every push and PR

**Job 1 — Lint (flake8 + black)**

**Why:** Catch style violations and obvious errors before they waste CI minutes running tests. Fail fast and cheap.

**Job 2 — Test (pytest with coverage)**

Runs only if lint passes. Fails if coverage drops below 80%.

**Why:** Coverage threshold prevents the common failure mode where tests are added but don't actually cover the new code path.

### Deploy pipeline (`deploy_staging.yml`) — triggers only on merge to `main`

1. Re-run the test gate (never deploy untested code)
2. Build a Docker image, push to GitHub Container Registry
3. Deploy to staging via Fly.io rolling deploy (`--strategy rolling` means zero-downtime — new containers come up before old ones go down)
4. Run a smoke test against the live staging URL — if it fails, the workflow fails and the team is notified

**Why rolling deploy:** A blue/green or canary deploy would be ideal for production, but rolling is the right default for staging — it's fast, zero-downtime, and the smoke test acts as the gate.

### Secrets and API key handling

**Why this approach:** secrets must never appear in source code, build logs, or Docker images. The rules enforced here:

| Rule | Implementation |
|------|---------------|
| No hardcoded keys | All secrets in GitHub Actions Secrets (encrypted at rest, masked in logs) |
| Least privilege | `FLY_API_TOKEN` scoped to one app, not the org. Rotated quarterly. |
| No build-time baking | Secrets injected at container startup via `flyctl secrets set`, never as Docker build args |
| Separate staging/prod | Different tokens, different app names, different GitHub Environments with separate protection rules |
| Secret scanning | GitHub's native secret scanning enabled on the repo |

### Rollback plan — first 5 minutes when production breaks

**Why rollback first, investigate second:** every minute of production downtime costs more than the time spent on root cause analysis. Get users unblocked first.

**T+0:00 — Confirm scope (30 seconds)**
```bash
flyctl logs --app my-prod-app | tail -100
```
Is it a complete outage (5xx on all requests) or partial degradation? This determines whether you rollback immediately or have 2 minutes to investigate.

**T+0:30 — Rollback to last known good image**
```bash
flyctl releases list --app my-prod-app       # find last good SHA
flyctl deploy --image <previous-sha> --strategy rolling --app my-prod-app
```
If the bug is behind a feature flag — disable the flag first. Instant, no redeploy needed.

**Target: production restored within 3 minutes.**

**T+2:00 — Confirm recovery with smoke test**
```bash
STAGING_URL=https://my-prod-app.fly.dev python part3_cicd/smoke_test.py
```

**T+3:00 — Communicate**
Post to incident Slack channel: "Rollback complete at T+X. Investigating root cause." Update status page to "Investigating."

**T+5:00+ — Root cause analysis (users are now unblocked)**
`git diff <good-sha> <bad-sha>` → pull structured logs → reproduce in staging → write regression test → fix → merge.
